When the hash and the name keep changing

A rule on a known hash catches one copy of a program. What catches the next three, when each has a new hash and a new name? This page replays one scenario from a synthetic sample: generated events, not a run on real machines.

Replay

Four copies, one incident?

Pick how many copies have run. By default every copy is renamed, as an attacker would do; tick “Keep one name for every copy” for the easier case.

One harmless test program is rebuilt and renamed four times, so every copy has a new SHA-256 and a new name. A rule on the known hash catches only the first copy, and scoring risk per name never adds up; rules on what the program does, scored per the address every copy calls, catch all four as one incident. With JavaScript this panel replays it copy by copy.

How the incident generator works

The same four steps for every scenario, so a rule is judged against what really happened, not against what it was meant to catch.

  1. Scenario

    A YAML file: ATT&CK techniques in order, and the detections each step is expected to raise.

  2. Events

    The generator writes the Windows (Sysmon) events each step would leave, plus a ground-truth record: time, host, technique, hash.

  3. SIEM

    Sigma rules match single events; OpenSearch Alerting monitors count across them and score risk per entity.

  4. Report

    Ground truth against findings, per technique: detected or missed, and how long it took.
